# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Gregal is a .NET 10 Worker Service that receives bingo-hall session results ("historicos de partidas") and upserts them into a Firebird database. It understands two unrelated wire protocols, each its own `IHostedService`, enabled independently by config: a single-message JSON/CSV protocol over TCP and/or RS232 (the original design), and an event-stream RS232 protocol (`*CODIGO<valor>#`, one tiny event per ball/prize/etc., shared with the `Vaprel.PidFullHD` screen software) that accumulates a whole game before saving it — **this second one is the primary/default receiver today**. It doubles as a Windows Service (`GregalReceiverService`) in production. Solution: `Gregal.slnx` → `Gregal/Gregal.csproj` (the service) + `Gregal.Tests/Gregal.Tests.csproj` (xUnit tests).

## Architecture

### Three hosted services, enabled independently by config

`Program.cs` conditionally registers up to three independent `IHostedService` implementations, gated by two config flags (not by the vestigial `NetworkSettings.Mode`):

- `TagProtocolSettings.Enabled` → `Networking/TagSerialGregalReceiver.cs` — the event-stream protocol (`*CODIGO<valor>#`), its own RS232 port. **Enabled by default; today this is the only receiver actually running** (current `appsettings.json` has `NetworkSettings.Enabled=false`).
- `NetworkSettings.Enabled` → both `Networking/TcpGregalReceiver.cs` (TCP) and `Networking/SerialGregalReceiver.cs` (a second, independent serial port) — the original single-message JSON/CSV protocol. Disabled by default; kept for halls whose hardware still speaks it.

All three share the same `HistoricoRepository` (and the JSON/CSV pair also shares `GregalParserEngine`), but there is no shared base class or common interface between any of them (an earlier `Worker`/`IGregalReceiver` abstraction was removed as dead code) — each is a standalone `IHostedService`.

### JSON/CSV pipeline (`TcpGregalReceiver` / `SerialGregalReceiver`)

```
raw bytes → string accumulator → split on delimiter → GregalParserEngine.Parse()
   → ping short-circuit, else JsonGregalParser or CsvGregalParser (IParser) → ParseResult
   → HistoricoRepository.SaveHistoricoAsync(ParseResult.Data) → GregalProtocolFactory response
```

- One message = one immediate response, synchronously, on the same connection/port.
- Framing delimiter: `\0` for TCP (hardcoded) and `NetworkSettings.SerialDelimiter` for its own serial port (configurable, defaults to `\0`). Buffers are bounded by `NetworkSettings.TcpMaxBufferChars`/`MaxBufferChars`; exceeding it clears the buffer and replies `BUFFER_EXCEEDED`.
- `GregalParserEngine` (Parsing/GregalParserEngine.cs) sniffs the raw string, ignoring whitespace: `"operation":"ping"` / literal `ping` → pong; starts with `{` → `JsonGregalParser`; anything else → `CsvGregalParser`. **`CsvGregalParser` only fills a handful of `HistoricoDTO` fields by fixed column index** (msg_id, codSala, codConc, fecha, partidaDia, precio, venta, caja, bolas) — it's a partial legacy shim, not at parity with the JSON path.
- Both parsers call the shared `Parsing/HistoricoDtoValidator.ValidateRequiredFields` before returning a `ParseResult`, rejecting a `HistoricoDTO` that's missing `CodSala`/`CodConc`/`PartidaDia`/`FechaSesion` (the fields that make up the Firebird upsert key below) instead of letting an ambiguous `0`/empty key reach the database.
- Responses are always a `GregalResponse` JSON object serialized with a trailing `\0` (see `GregalProtocolFactory`), even on error — the client must never be left waiting.
- `TcpGregalReceiver.IsIpAuthorized` is fail-open by design: an empty/missing `NetworkSettings.AllowedIps` allows any IP ("empty = unrestricted"). Current config restricts to `127.0.0.1`; know this before clearing the list in a real deployment.

### Tag event-stream pipeline (`TagSerialGregalReceiver`) — primary protocol today

A different shape entirely: instead of one message per game, the hall hardware emits **dozens of tiny framed events per game** (`*E19#` = ball 19 drawn, `*C307#` = price, `*F#` = end of game, ...). There is no response — the original transport is one-way (UDP-derived, no ACK) and this receiver never writes back to the serial port.

```
raw bytes → _accumulator → split on TagProtocolSettings.FrameDelimiter ('#')
   → TagEventParser.Trocear() (also splits on '*') → TagEventParser.Parse() → TagEvent
   → PartidaAccumulator.Feed()
   → (only on event 'F') HistoricoDTO → HistoricoDtoValidator
   → _persistChannel → PersistLoopAsync → HistoricoRepository.SaveHistoricoAsync
                                            (failure → appended to TagProtocolSettings.FallbackFilePath)
```

- **Framing is resilient to a lost `#`.** Every event starts with `*`, and `*` can't appear inside one (text values seen in real captures never contain it, and every byte of the binary `e` payload has bit `0x80` set), so `TagEventParser.Trocear` also splits on `*`: `*H4000junk*F` still yields the `F` and closes the game instead of leaving it open and merging it with the next one. Anything before the first `*` in a `#`-delimited chunk can't be a complete event and is discarded — logged as a warning, except right after opening the port or a buffer overflow, when it's just the expected tail of an event already in progress. This replaced an older rule that discarded the *whole* first chunk after opening the port (which used to swallow a valid `*T1#` sent first).
- Numeric values are parsed as **digits only** (`NumberStyles.None`): the protocol never sends anything else (amounts are integer cents), and the previous `NumberStyles.Any` silently accepted number-looking garbage (`4e1` → 40, `4,000` → 4000, `(400)` → -400). Anything else (e.g. `*H4000junk#`) is not guessed: the field is dropped and `PartidaAccumulator` logs a warning with the event code and the full raw value (for `D`/`u`, including the line-type digit, which must itself be a digit). A bare `*D#` (an MCB marker) is ignored without a warning. Noise that turns one digit into another can't be detected — text events carry no checksum; only the binary `e` snapshot does.

- `Parsing/PartidaAccumulator.cs` is stateful (one singleton instance, reused across games): it holds the in-progress game and only emits a `HistoricoDTO` on event `F`. Most of the mapping was confirmed on 2026-10-14 against a real 7-game capture from the Metronia hall and the tickets the machine itself prints per game (`Gregal.Tests/PartidaAccumulatorTests.cs`, `Feed_ConPartidaRealCompleta_CoincideConElTicketImpresoPorLaMaquina`) — notable confirmed decisions:
  - `C` (price) and the monetary `PremioCodeMap` codes (`L`, `p`, `A` — line, line-plus, prima) arrive in **cents**, not euros; `Finalizar()` divides by `10^NumDecimales` (from event `K`, defaulting to 2 if absent). `M` (ball-count cap for the prima prize, `PremioCodeMap["M"]` = `PREMIO7`) is explicitly excluded from that division — it's a ball number, not an amount. `Venta` isn't sent by either manufacturer: `Finalizar()` computes it as `Vendidos * Precio` right after converting `Precio` to euros (2026-10-30; 0 for a game without its header). `Q`→`Caja` was left untouched — it never appeared in the real capture, so there's no evidence either way for its unit.
  - **Two different hardware manufacturers exist in the halls** (confirmed 2026-10-14, fourth round), with similar but non-identical protocols — Metronia (the 7-game capture above) and MCB (`VolcadoMCB.txt`). This explains what first looked like a contradiction: on Metronia, `PREMIO5`=line-plus (`p`), `PREMIO6`=prima (`A`), `PREMIO7`=prima ball cap (`M`), cross-checked against real ticket amounts; on MCB, the *same letters* carry no reliable value — they repeat constantly as junk/zero noise (`*M0#*A0#*A000#...`, several times between every single ball) rather than once per game with a real amount. This is selected **per sala** with `TagProtocolSettings.Fabricante` (`"Metronia"` default / `"MCB"`): with MCB, `AplicarSiEsPremioMapeado` drops `A`/`M`/`p` (`CodigosSegunFabricante`) even if they're in `PremioCodeMap` — the manufacturer overrides the map for those three codes. Independently of the manufacturer, those three are never logged as "unmapped" when absent from the map (MCB repeats them constantly and would flood the log). The site installer asks for the manufacturer and writes just this key. Don't try to switch to MCB by overriding `PremioCodeMap` in `appsettings.Development.json`: .NET configuration *merges* dictionary keys across files, so it can't remove entries — use `Fabricante`. `G`, `S`, `R` are **not** manufacturer-dependent, just confirmed-ignored on both (removed from the default map; the explicit `case` in `Aplicar` no-ops them before they'd ever be looked up there).
  - **`*E101#` is the "bola plus"** (clarified by the user 2026-10-30; it had been taken for noise because the `'e'` snapshot doesn't change): not a drawn ball — it's not added to `Bolas` nor counted in `Extracciones` — but the number of balls drawn at that moment goes to `PREMIO17` (`Premios[16]`, `IndicePremioBolaPlus`), first occurrence wins, and it's excluded from the cents division in `Finalizar()` like `M`. In the MCB capture it appears at most once per game (games 2, 4, 7, 8, 10 → 41, 6, 57, 26, 6). Any other `E` value outside 1-90 is discarded as noise before touching `_bolasOrden`.
  - A ball that arrives twice in the same game is ignored with a warning (decided with the user 2026-10-21: it can't really be drawn twice, so it's noise such as a retransmission). A ball removed with `Z` is unmarked, so receiving it again is accepted without warning.
  - **Timestamps** (decided with the user 2026-10-30): on `T`, `Fecha` (`FECHA`, `TIMESTAMP`) = local date+time of that moment and `HoraVenta`/`HoraCierre` (`HORA_VENTA`/`HORA_CIERRE`, `TIME`) = its time as `HH:mm:ss`. `HORA_FIN` (`TIME`) is set by `HistoricoRepository.HoraFinAlGuardar` with the PC's time when the save transaction is prepared, only if the DTO doesn't already carry one (the JSON/CSV protocol may). A game without `T` has none of the three start fields. `HoraLinea`/`HoraBingo` = time of the first line / bingo call — `D<cartón>` / `H<cartón>` (Metronia) or `Y<cartón>` before / after the bare `*H#` (MCB, which never sends `D<cartón>`/`H<cartón>`: confirmed with the Blanes capture of 2026-10-29; `Y` sets them since 2026-10-30). `L`/`B` don't set them — they're the prize *amounts* and arrive in the header at ball 0. Cleared by `u`/`h` when no winner remains (no revert exists for `Y`). Both classes take an optional `TimeProvider` (defaults to `TimeProvider.System`) so tests can fix the clock. The `HoraX` DTO properties are strings; Firebird casts `HH:mm:ss` to `TIME` (verified end-to-end against `GREGAL_DEV.FDB`).
  - **Game boundaries and missing `T`** (2026-10-28, checked against all 11 MCB games): `*f#` only ever arrives *between* games, never between a `T` and its `F`, and `T` only at the start of a game. MCB sends **two** `*F#` per game (`…*F#*f#…*F#*f#…`). Rules: an `F` with no `T` and no balls/calls is ignored (MCB's second `F`, or a stray `F` when starting between games); an `f` arriving while the game has balls/calls means its `F` was lost, so the game is closed with a warning; a game closed with content but **no `T`** (capture started mid-game) is never given an invented number — the old in-process counter could overwrite a real game of the day through the `UPDATE OR INSERT` — but held in `_pendienteSinT` until the next `T=N` arrives and then emitted as game `N-1` (discarded with a warning if `N` is 1 or unreadable, or if the service stops first). Every such game is marked in `RECLAMACION` (`PARTIDA A MEDIAS: Nº DEDUCIDO, SIN CABECERA`, plus `, BOLAS APROX.` if the `e` snapshot added balls): its number is inferred and its header (price, cards, serie, prizes — all sent right after `T`) is missing. `Feed_ConCapturaRealDeMcb_DevuelveSoloLasOncePartidas` replays the whole MCB capture and expects exactly games 1-11. Metronia follows the same boundaries (7 games, `f` only between games) but sends a single `F`; `Feed_ConCapturaDeMetroniaEmpezadaAMitadDePartida_RecuperaLaPartidaUnoAlLlegarT2` cuts its capture at game 1's 10th ball and checks the game comes back whole (balls via the `e` snapshot, header lost) as game 1 when `T2` arrives. The captures in `Gregal/Docs/` are UTF-8 text of the raw bytes read as Windows-1252 — tests undo that (`LeerCaptura`) to get the original bytes.
  - `D<tipo><cartón>#` (line) / `H<cartón>#` (bingo): confirmed against real tickets. The **first digit of `D`'s value is a line-type code** (maps to a row letter S/C/I on the printed ticket), not part of the card number — stripped before storing `CartLinea`. `H`'s value has no such prefix.
  - A **second, newer protocol variant** (confirmed by the hall operator, third round) merges line and bingo into one code, `Y<cartón>#`, with no type digit — which one it means depends on whether `*H#` (bare, no value) has already been seen this game: before it, `Y<cartón>` is a line; after it, a bingo. `*Y#` bare keeps its original meaning ("entering verification", no DTO effect). `PartidaAccumulator` supports **both** variants side by side (`RegistrarCantoLinea`/`RegistrarCantoBingo` are the shared bookkeeping `AplicarCantoLinea`/`AplicarEventoY` both call) since different hardware/firmware in the same hall could emit either.
  - Multiple winners in the same game are possible (confirmed: a real game had two valid bingo cards) — `CartLinea`/`CartBingo` store a comma-joined list, same convention as `Bolas`.
  - `D`/`u` and `H`/`h` really are "tentative call, reverted if the next matching event is wrong" (confirmed by the user) — none of the 7 real games happened to have an incorrect call, so `u`/`h` don't appear in that capture, but the mechanism itself is correct as designed. No equivalent revert exists yet for the `Y`-based variant.
  - Fields: `K`→`NumDecimales`, `P`/`U`→`Del1`/`Al1` (first/last card sold), `X`→`Serie1`/`Serie2` (comma-separated if the print run splices two series), `J`→`Letra1`/`Letra2` via `TagProtocolSettings.SerieLetraMap`. `J`'s value can carry trailing garbage after the 4-digit code (e.g. `386400001&BIPLUSE1.255` → use only `3864`) — confirmed third round. **MCB never sends `X`**: its serie travels in `z` (serie 1) and `y` (serie 2 when the sale wraps into the next serie, `0` otherwise) — mapped only with `Fabricante=MCB` (2026-10-30; the operator had called `z`/`y` "morralla", but the capture proves it: `y` appears exactly when `P`..`U` wraps past the 3864-card serie from `J3864` and the counts add up to `V`, e.g. game 5 `P3801`-`U750` = 64 + 750 = `V814` with `z272327 y272328`, and the next game's `z` is that `y`; `Feed_ConCapturaRealDeMcb_DevuelveSoloLasOncePartidas` asserts all 11). `Y` (bare), `º`, `f` (heartbeat), and `G`/`S`/`R` are recognized no-ops with no `HISTORICO` equivalent — confirmed, not placeholders — specifically so they don't spam the log at Information level the way a genuinely unmapped code would.
  - `Z<bola>#` removes a ball already registered (hardware misread correction) — `_bolasOrden` is a `List<int>` rather than an append-only string specifically to support this. The hall operator confirmed `Z` exists and corrected an earlier transcription error that had called it `X` (which is unambiguously the serie field, confirmed separately) — but `Z` never appeared in the 7 real games, so this path is implemented from the description alone, not validated against real traffic.
  - `EstadoPartidaDecoder` is **validated against real data**: Metronia snapshots start with marker `0x8F` (not in the `CadenaEstado.cs` reference, which only has `0x8D`/`0x8E`) and otherwise use the `0x8E` layout. All 1,469 snapshots in the Metronia capture pass the checksum and match exactly the balls received via `*E#` up to that point (reconstruct the bytes from that `.txt` by re-encoding each character as Windows-1252). Byte 14 is *not* the last ball on Metronia, so `UltimaBola` is null for `0x8F`; the phase bit (`JugandoLinea`) isn't validated for Metronia either — Gregal uses neither. MCB uses `0x8E`; its empty-state snapshot decodes correctly. Before this fix every Metronia snapshot was rejected: a warning per snapshot (~200 per game) and mid-game reconnection didn't work.
- Event `e` (lowercase) is a binary "game snapshot" used so a receiver that starts mid-game can catch up — decoded by `Parsing/EstadoPartidaDecoder.cs` (bit-packed ball mask + checksum, reverse-engineered from the external `CadenaEstado.cs` reference class, not part of Gregal). `PartidaAccumulator` merges in only the *newly learned* balls (balls already seen via real `E` events keep their real draw order; balls recovered only from the snapshot are appended in ascending order as an approximation) and marks the game as partially recovered in `Reclamacion` (capped at 64 chars — `HISTORICO.RECLAMACION` is `CHAR(64)`, fixed-length, confirmed via `RDB$FIELDS`).
- The serial port uses `Encoding.Latin1` (not the default ASCII/UTF-8) so bytes ≥ 0x80 in the binary `e` payload pass through unmodified — load-bearing, do not change it.
- Two-stage `Channel` pipeline (`_messageChannel` then `_persistChannel`) decouples serial reading from Firebird writes, so a burst of fast games never blocks ingestion. If `SaveHistoricoAsync` fails or returns `false`, the DTO is appended as JSON to `TagProtocolSettings.FallbackFilePath` instead of being lost (no automatic retry from that file back into Firebird — manual recovery only).
- `TagSerialGregalReceiver.Stop()` and `SerialGregalReceiver.Stop()` both guard against being invoked twice concurrently (`_stopLock`/`_detenido` fields) and swallow (log, don't throw) any exception from `SerialPort.Close()`/`Dispose()`. This exists because `Stop()` can be called from both `StopAsync` (host shutdown) and the listener loop's own `finally` at nearly the same time, and `System.IO.Ports.SerialPort` has a known internal `NullReferenceException` when closed/disposed concurrently — it used to crash the whole process on Ctrl+C. Preserve this pattern if you touch either class's shutdown path.
- `TagProtocolSettings.DefaultCodSala`/`DefaultCodConc` are placeholders (currently `1`/`1`, for testing) because the tag protocol carries no sala/concesión identity at all — a real deployment must set real values, and a single Gregal instance currently supports exactly one sala.

### Persistence

`Data/HistoricoRepository.cs` does a single Firebird `UPDATE OR INSERT ... MATCHING (COD_SALA, COD_CONC, FECHA_SESION, PARTIDA_DIA)` against `HISTORICO`, inside a transaction, with the 99 `PREMIOn` columns built dynamically (`HistoricoDTO.Premios` is a `decimal?[99]`). All writes, from any of the three receivers, go through a single process-wide `static SemaphoreSlim(1,1)` so concurrent inserts never overlap — if you touch this method, preserve that serialization or justify removing it. Connection/transaction failures are caught and logged with sala/partida context, returning `false` rather than throwing.

Numeric columns that didn't arrive are written as **0, not NULL** (decided with the user 2026-10-30): all nullable `int?`/`decimal?` DTO fields go in as `?? 0`, the 99 `PREMIOn` included, and `HORA_CIERRE_H`/`FECHA_SESION_MES` (INTEGER columns, string DTO fields) via `EnteroOCero`. Exception: `NUM_DECIMALES` falls back to 2 (`DecimalesPorDefecto`), because `PartidaAccumulator` already divided the amounts by 100 when `K` was missing — 0 would claim they have no decimals. Text (`LETRA*`, `GUIABOLAS` — it's `CHAR(64)`, not numeric —, `RECLAMACION`, `BOLAS`, `CART_*`) and date/time columns stay NULL. The 7 numeric `*_VIR` columns (`SERIE_1_VIR` … `VENDIDOS_VIR`) were added to the `UPDATE OR INSERT` on 2026-10-30, after confirming they exist in the Blanes sala's `aamslog.FDB` too; `LETRA1_VIR`/`LETRA2_VIR` (text) are left out and stay NULL. **Any column added to that statement must exist in every sala's `HISTORICO`**, or every save there fails — check the sala schema before adding one.

`HISTORICO.BOLAS` is `VARCHAR(255)` in salas' pre-existing databases (the template has `VARCHAR(300)` via `Docs/Migraciones/2026-10-08_ampliar_bolas.sql`); 90 balls take 260 chars, so a game with ~86+ balls would be rejected whole ("string right truncation"). Since altering the sala's own database isn't always acceptable (decided 2026-10-29: the Blanes sala's `aamslog.FDB` stays at 255), `AjustarBolasALaColumna` cuts the list to the first whole balls that fit `DatabaseSettings.MaxLongitudBolas` (default 255; set 300 where the migration was applied), prepends `BOLAS RECORTADAS` to `RECLAMACION` (capped at 64), and logs a warning with the full list. It works on local copies — the DTO is left intact so a failed save still sends the full list to the fallback file. Real games in the captures used 47-72 balls (≤ 210 chars).

### Configuration

Four strongly-typed options sections bound from `appsettings.json` via `IOptionsMonitor<T>` (Config/*.cs): `GeneralSettings`, `NetworkSettings` (TCP + its own serial port, gated by `NetworkSettings.Enabled`; `Mode` is vestigial/unused), `TagProtocolSettings` (its own separate serial port, gated by `TagProtocolSettings.Enabled`), `DatabaseSettings`. The two `Enabled` flags default differently (`NetworkSettings.Enabled=false`, `TagProtocolSettings.Enabled=true`) to match today's "tag protocol is primary" deployment.

The Firebird connection string in `appsettings.json` currently embeds a plaintext password (committed to git history, not just the working copy) — be careful not to further propagate that value when editing nearby code. `Gregal.csproj` has a `UserSecretsId` but it isn't actually used to keep the password out of the file; `Deploy/Instalar-Gregal.ps1` writes a new connection string straight into `appsettings.json` on-site, the same plaintext-file pattern.

The connection string also sets `Charset=ISO8859_1` explicitly (added 2026-10-15), matching the database's actual charset (confirmed via `RDB$CHARACTER_SET_NAME`) — without it, the Firebird client defaults to `NONE`, which doesn't translate accented characters/`ñ` and can corrupt text fields on write or read (surfaced when opening the database in a third-party tool, which warned about it explicitly; verified by round-tripping accented text through `HISTORICO.RECLAMACION`).

Two databases, on purpose: `Gregal/Data/GREGAL_EMPTY.FDB` is the **versioned, always-empty template** the site installer copies for a new sala — never write test data into it. Local development uses `Gregal/Data/GREGAL_DEV.FDB` (gitignored; create it by copying the template), selected through `appsettings.Development.json`, which only applies under `dotnet run` (`DOTNET_ENVIRONMENT=Development` from `launchSettings.json`). The installed Windows Service runs as Production and uses `appsettings.json`, whose `Database=` path the installer rewrites per sala.

### Startup banner and PC diagnostics

`Program.cs`'s `MostrarBannerDeArranque` (console-only, skipped under `WindowsServiceHelpers.IsWindowsService()`) prints which protocol(s) are active, their ports/sala config, and warns if something's missing or a configured `ComPort` isn't visible on this machine. `Diagnostics/InfoSistema.cs` supplies the RAM/disk-free numbers (via a `GlobalMemoryStatusEx` P/Invoke) — a quick sanity check before deploying to a sala's PC.

### Deployment

`Deploy/Instalar-Gregal.ps1` installs Gregal on a new sala's PC from a published folder: checks for the .NET 10 runtime, prompts for network/serial/DB settings, rewrites `appsettings.json` in place (regex-based, preserving its `//` comments rather than a JSON round-trip), registers and starts the Windows Service, opens the TCP firewall port, and tails the resulting log. It warns (and asks) if the service already exists, since it re-asks every setting.

**Preferred distribution: the Inno Setup installer** (`Instalador/Gregal.iss`, built by `Instalador/Crear-Instalador.ps1`, which publishes, extracts `GREGAL_EMPTY.FDB` from `HEAD` — never the working copy — and passes `<Version>` from `Gregal.csproj`; requires Inno Setup 6). One `.exe` installs or updates depending on whether the `GregalReceiverService` service already exists (`ServiceName` is overridable with `/DServiceName=` — use that to test against a throwaway service instead of a real one). Fresh install: copies files and runs `Instalar-Gregal.ps1` for the sala questions. Update: install folder taken from the service's `ImagePath` (so salas installed with the scripts update in place), service stopped in `PrepareToInstall`, files replaced with `appsettings.json` and `GREGAL_EMPTY.FDB` marked `onlyifdoesntexist uninsneveruninstall`, new config dropped as `appsettings.json.nuevo`, service restarted; an unchecked post-install option re-runs `Instalar-Gregal.ps1`. Uninstall stops and deletes the service (and any `Gregal TCP *` firewall rule) but keeps config, logs and database. `AppId` must never change between versions.

`Deploy/Actualizar-Gregal.ps1` (zip-based alternative to the Inno updater) updates an existing installation **without touching the sala's configuration**: the new zip is unzipped to a *different* folder and the script run from there (it refuses to run from the install folder — unzipping over the install is exactly what used to clobber `appsettings.json`). It finds the install folder from the service's `binPath` (or `-InstallDir`), stops the service, backs up everything except `logs\` and `.FDB` files to `<install>\_backup\<timestamp>\`, copies the new files except `appsettings.json` and any `.FDB` that already exists, drops the new config as `appsettings.json.nuevo` for reference, lists config keys the new version has that the sala's file lacks (Gregal falls back to the options class defaults for those), and restarts the service. `-SobrescribirConfiguracion` replaces `appsettings.json` too. Both scripts are copied to the publish root by `Gregal.csproj` (`Deploy\*.ps1`) and must keep their **UTF-8 BOM** — Windows PowerShell 5.1 reads BOM-less scripts as ANSI and garbles the accented messages. `Gregal/Docs/Migraciones/` holds hand-applied Firebird schema migrations (e.g. widening `HISTORICO.BOLAS` to `VARCHAR(300)`, since the tag protocol's long ball lists overflowed the original `VARCHAR(255)`) — these are **not** applied automatically and must be run manually against any already-deployed database.

### Logging

Serilog, configured entirely in `Program.cs` (not appsettings-only): console + daily rolling file under `<exe dir>/logs/`, path derived from `GeneralSettings.LogPath`. The first line of each run is `Gregal <InformationalVersion> arrancando (servicio de Windows|consola)`, to tell which build a sala is running. `AppDomain.UnhandledException` logs any exception that escapes every `try/catch` as `[FTL]` and flushes before the process dies (otherwise it only reaches the Windows Event Viewer), `TaskScheduler.UnobservedTaskException` logs and observes, and `host.Run()` is wrapped so a fatal startup error is logged, sets exit code 1 (so the service's `sc.exe failure` recovery applies) and `Log.CloseAndFlush()` always runs. A log that simply stops with no shutdown line and no `[FTL]` means the process was killed from outside — in the field, typically the hall's nightly power-off (confirmed 2026-10-28 via System event 1074). Note: `appsettings.json`'s `"Logging":{"LogLevel":"Debug"}` has no effect on Serilog — `ReadFrom.Configuration` only looks for a `"Serilog"` section, which doesn't exist here, so the effective minimum level is Serilog's own default (Information) regardless of what `"Logging"` says.

### Protocol reference

Full wire-format spec for the original JSON/CSV protocol (fields, examples, error codes, reconnect/heartbeat semantics) lives in `Gregal/Docs/Specs.md` and `Gregal/Docs/Dev_Anotaciones.txt` — read these before changing anything in `Protocol/` or the parsers, since external bingo-hall clients depend on this contract. The tag event-stream protocol has no written spec in this repo; its behavior is inferred from external reference classes (`Comunicaciones.cs`, `Mensaje.cs`, `CadenaEstado.cs` — not part of Gregal) and a single real example game captured in `Gregal.Tests/PartidaAccumulatorTests.cs`. Treat that test as the source of truth, and expect some less-common field/premio-code mappings to need correction once validated against real hardware in a sala.
